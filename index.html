Cross-Cutting Migration Playbook: Day-0 Hybrid Landing Zone (IPAM / Split-Horizon DNS / Interconnect) & 24-72h Post-Cutover Soak Gate

Target-State Reference Every hybrid or multi-cloud migration succeeds or fails at two bookends rarely shown in high-level diagrams: Day-0 network/identity readiness before moving the first workload, and a quantitative post-cutover soak gate before retiring legacy infrastructure. This cross-cutting checklist completes the closed-loop migration lifecycle across all five blueprints without claiming permanent 24/7 SRE on-call ownership.

A. Day-0 CIDR / IPAM & Split-Horizon DNS Pre-allocate non-overlapping RFC 1918 CIDRs across on-premise data centers, cloud VPCs, and Kubernetes Pod/Service pools so peering or future M&A never triggers NAT workarounds. Enforce Split-Horizon DNS separating internal private endpoints (DBs, Harbor, GitLab) from public ingress, lowering DNS TTLs (e.g., 60s) 24-48h before cutover.
B. Private Interconnect & Zero Public DB Exposure Anchor hybrid traffic over redundant private links (route-based IPsec VTI with DPD/MSS clamping, AWS Transit Gateway / PrivateLink, GCP Cloud Interconnect, or Alibaba Express Connect) with strict security groups and zero direct public internet exposure on database tiers.
C. 24-72h Quantitative Post-Cutover Soak Window Validate cutover stability against hard exit criteria before closure: p95 / p99 API latency parity against pre-migration baseline, 5xx error ratio below threshold (< 0.1%), DB connection pool saturation below ceiling (< 70%), zero replication lag drift, and verified row-count / checksum parity.
D. Controlled Legacy Decommission Gate Keep legacy VPS/VMs in warm read-only standby throughout the soak window to guarantee instant rollback. Execute deterministic teardown (final immutable backup snapshot, DNS/SSL revocation, orphan volume/EIP removal) only after written soak sign-off and internal team handover.

Sovereign PostgreSQL DBaaS v3 & Pattern 1 Multi-Store Trade-Off Matrix (Why DB-per-Store + Swarm/OpenVPN)

Target-State Reference Evaluating how multi-store retail Odoo 17 POS scales across separate ISPs with dynamic IPs without sacrificing ACID accounting integrity or risking database corruption:

Retail Store Pattern Data Corruption & Blast Radius Filestore & PITR Hygiene ISP Outage Resilience
Pattern 1: Isolated DB-per-Store (Selected) Highest integrity: single-primary ACID write path, zero multi-master conflicts, 100% tenant blast-radius isolation (store1..storeN). 1 container = 1 local volume (zero NFS lock corruption); independent per-store Barman PITR recovery. Cashier resilience via Odoo 17 POS browser IndexedDB offline queue + 4G/5G router failover.
Pattern 2: Single Shared DB (Multi-Branch) Single ACID source, but schema upgrades or bad queries impact every branch simultaneously. Multi-replica Odoo requires shared NFS/GlusterFS filestore, risking attachment/PDF desync on lock stalls. Same POS IndexedDB queue, but single-DB maintenance freezes all branches together.
Pattern 3: Autonomous Edge DB + Sync Highest corruption risk: bidirectional sync risks sequence collisions, negative stock, and partial accounting journal entries. Each store requires local HA + backup governance; attachment/receipt sync adds operational fragility. Full back-office continuity during long ISP blackouts, at steep reconciliation complexity.
1. Multi-ISP OpenVPN PKI + Swarm Overlay (MTU 1300) Hub-and-Spoke OpenVPN (AES-256-GCM, tls-crypt, float, static CCD 10.88.0.x) stabilizes Swarm Raft (--advertise-addr / --data-path-addr on tun0) across rotating ISP IPs, disabling redundant IPsec ESP encryption and clamping overlay MTU to 1300 to prevent VXLAN WAL fragmentation.
2. Zero-iptables Routing, PgBouncer & Docker Secrets Replaces OS-level iptables DNAT SPOFs with multi-replica Role-Aware HAProxy (HTTP :9201 probe separating :54322 RW, :54323 RO, and overlay-only :54321 Barman), PgBouncer (:6432 per-store session pool + * transaction pool via SECURITY DEFINER lookup), and 13+ Docker Secrets.
3. External repmgrd Auto-Failover & Sync Fallback Runs external repmgrd daemons inside barman_control using SSH keypair secrets with synchronous_standby_names = 'FIRST 1 (<peers>, barman_receive_wal)' and restart_policy: none on pg_db1..dbN to prevent split-brain on host reboot.
